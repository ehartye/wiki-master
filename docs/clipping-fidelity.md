# HTML clipping fidelity

`clip.mjs` uses an owned extraction wrapper with pinned Defuddle 0.19.5, linkedom 0.18.12 and Turndown 7.2.0. Development uses `npm ci`; installed plugins acquire the same versions through npm exec when local dependencies are absent. The fetcher retains Defuddle's proxy support, encoding detection, size/time limits and bare-request bot retry. English remains explicit on every request.

Before extraction, the wrapper preserves meaningful fragment-linked API heading text. Recognized documentation structures select their enclosing content container, preserve introductions outside `<article>`, and turn warning/availability boxes into blockquotes before readability cleanup. Navigation, footers, hidden controls and buttons are removed. Ordinary articles retain default readability selection. Rendered HTML follows the same path, with the original URL supplied for relative links.

The source-to-output check examines visible headings, recognized callouts and availability notices, API introductory paragraphs and feature-list items. It looks for normalized text at the start and end of each item (up to fourteen words at each end). A missing probe saves the clip with `fidelity: partial`, prints the missing item's kind and label, and queues a `fidelity` triage issue linked to the raw file. `fidelity-checks` records the number of source items examined, including zero when none were recognized. Credibility (`quality`) is independent.

**Page chrome is set aside, not hidden.** A site's feedback widget, share row or sidebar is removed by the extractor on purpose, and counting each as a lost heading queued a triage entry for nearly every Microsoft Learn clip. A missing heading is now set aside, not counted as loss, only under one of these narrow rules, and each set-aside is recorded: `fidelity-ignored: <count>` in the clipping's frontmatter, the labels on stderr, and `fidelityAssessment.ignored` (label and reason) in the result. (1) It restates the page title, which the clipping keeps in its frontmatter (every word of the heading is a word of the title, or it starts with such a heading). (2) It is the whole heading `Feedback`, `Share`, `Read next`, `Related posts`, `Recent posts` or `Stay informed`, with at most 40 non-link words before the next heading. (3) On `github.com` only: GitHub's own chrome headings (`Repository navigation`, `Reviewers`, `Labels`, `About`, `Conversation`, a participant count and the rest of the sidebar), with the same size limit, and a comment byline (`X commented ...`) whose comment body, its longest run of at least eight non-link words, was captured. (4) It sits inside a container whose id or class names a sidebar, menu, dropdown, table of contents, navigation, breadcrumb, widget, promo or banner (a container above the content root does not count), with the same size limit measured within the container. Anything else still warns: `Applies to`, `Remarks`, `Syntax`, a `Share your results` section, a `Feedback` section with a body, a heading in a menu with a long body. On a sample of five real pages (2026-10-26) the warnings fell from 1, 1, 14, 14 and 18 to 0, 0, 0, 2 and 0; the two that remain are comment bylines whose bodies are mostly links, which the check could not confirm were captured until 0.71.0 (next paragraph). This is a judgement about site layout and can be wrong: a real content section named `Feedback` that the extractor drops, with under 40 words, would be set aside, which is why the count is recorded.

**Three more cases, from a second sample (0.71.0).** (5) On `github.com`, the hidden dialog heading `Choose a reason for hiding this comment` is interface text. (6) On `github.com`, a comment byline (`X commented Oct 1, 2023` or `X left a comment`) is set aside when the comment header the clipper wrote is in the clipping: the clipper rewrites a byline to `**X** · 2023-10-01`, so the heading text is never found, and a comment that is only links or a bare review header has no run of prose to prove its capture. The proof is the bold author and, when the heading has a date, that date in ISO form; a date that cannot be read (`3 days ago`) is not accepted. (7) On any host, a short heading (at most three words, no digit) whose whole section text appears in the clipping, in order, has lost only its label: every non-overlapping five-word window of the section's text (links included, 10 to 150 words, at least two windows) is found as whole words. A byline is never only a label, since it says who spoke and when. Measured on seven real pages fetched 2026-10-26: an Epic API page 1 to 0 warnings (its `Navigation` section is a table that was captured), two public GitHub pull requests 2 to 0 and 6 to 1, and three more Epic pages unchanged at 0, 2 and 1 warnings. The unchanged ones are real partial losses and must keep warning: on an Epic page two headings sit over lists of child topics whose descriptions were dropped (0 of 7 and 0 of 5 windows found), and a `Prerequisite topics` callout is gone entirely. The one left on the second pull request is a hidden dialog whose section runs on into a following comment. NVIDIA support pages answer a plain request with 403 and could not be measured.

**Two losses fixed on Epic documentation pages (0.74.0).** Both were real partial losses that the check had reported correctly. (a) A `<block-callout>`, Epic's note, warning and "Prerequisite topics" box, is kept as a blockquote and is now an expected callout. A box above the first section was dropped whole, because the default content choice cuts it off; a page that has one now has its content root fixed, which also brings the banner image with the title block. It does not switch the page to the documentation pipeline, which would also keep the community footer. (b) A child-topic card (`a.document-list-card`: thumbnail, title, one-line description) becomes `- [Title](url): description`; it kept only the title, as a linked image. Measured on twelve Epic pages fetched 2026-10-26: the four pages that had fidelity warnings (1, 2, 1 and 3) have none now, the other eight had none before and have none, five pages extract byte-identically, and no footer text was added. Existing clippings are not repaired: a re-clip of the page picks the fix up.

Recognized GitHub REST reference layouts also preserve endpoint columns that Defuddle's `.gutter` removal rule otherwise deletes. Method/path summaries become code spans, parameter captions remain next to their tables, and supplied request/response examples become fenced code blocks with line breaks and language metadata. The audit checks whole normalized parameter rows and endpoint summaries in addition to the bounded heading/notice probes. Code examples are checked literally, retaining case, punctuation and line boundaries (CRLF and LF are equivalent). Exact example preservation is also tested against fixture text.

This is a bounded structural check, not a completeness score. It can miss loss within a long ordinary item, miss unrecognized structures, or flag a harmless formatting change. It cannot inspect content absent from the supplied HTML or hidden behind an unselected UI tab. A long clip or zero warnings does not establish complete capture. Existing raw clippings are immutable and are not rewritten by this release.

Offline regression fixtures cover Three.js BufferAttribute and GLTFLoader, GitHub Pages availability/public-site warnings, and Sharp installation cautions. Full served HTML from those four URLs was also checked on 2026-10-19: 49, 47, 16 and 26 structural items respectively, with no missing probes after preservation. These observations establish the reproduced repairs, not a general fidelity guarantee. Fixture provenance is in `test/fixtures/documentation/README.md`.

On 2026-10-20 the official artifacts and workflow-runs REST reference pages were checked end to end: five and nineteen endpoint sections, 95 and 355 structural items, and all 13 and 46 supplied visible examples respectively survived. The artifact page previously reduced to 541 Markdown characters. Its repaired capture is 16,670 characters; the workflow-runs capture is 112,352. These lengths are observations, not acceptance criteria or completeness guarantees. Neither page needed browser rendering. The release does not claim that all interactive response-schema tabs or alternate language examples have been captured.

## Pages that are not the page, text files and binaries (0.81.0)

**A login, consent or age-gate page.** A page with words enough to clear the thin floor can still be the gate and not the page. `classifyInterstitial` (`scripts/lib/interstitial.mjs`) flags a text with at least 5 gate phrases (log in, sign up, verification link, technical cookies, enter your birth date, mature content and the like), at least 3 per 100 words, and less than half of its title words in the body; a title with no word of five letters or more cannot be judged. [measured] Replayed over the 5,886 HTML clippings of one vault: it flags exactly the three known shells (two sound-library pages that shared one body, and a store age gate), 5.4 to 6.4 phrases per 100 words and none of the title in the text; the next highest pages had 2.86, 2.61 and 2.47 per 100 words and their titles in full. A flagged page is not written, a `wrong-node` row says why, and the URL is not declined. It runs on the clipper and on the HTML repair route. It is a body-only signal: a gate with few of those phrases, or whose title it repeats, passes.

**A text file.** Defuddle cannot read one, so a URL that looks like a text file (a text extension, or any path on the raw GitHub host; a `github.com/.../blob/...` view is a web page) is fetched for its bytes by a child process and kept whole in a fence (longer than any run of backticks inside), with `extraction: plaintext`. [measured] A checksum manifest, a dotfile and a package.json served as text/plain all failed the static read before this. A file over 1 MiB, or one with a NUL byte or 2% undecodable text, is refused and queued as `attention`. A text URL that answers with HTML, or that cannot be fetched, goes to the ladder as before. The HTML repair route does not re-read a plain-text clipping.

**A binary file in a GitHub capture.** `clip-gh` excluded binaries by extension only; `.glb`, `.fbx`, `.aseprite`, `.ase`, `.psd` and `.ogg` were missing, and a binary under another name was clipped as text. It now also excludes a file with a NUL byte or 2% undecodable text. [measured] Over 6,788 clippings of one vault: 37 held a NUL byte, 35 of them GitHub captures (27 `.glb`, 7 `.fbx`, 1 `.aseprite`). Triage now lists such a capture as a `fidelity` row naming its exact path; no source summary hash is created for it.

## Recapture, saved pages, and the decline and known-URL commands (0.87.0)

**A second capture of a page already clipped: `clip.mjs <url> --recapture`.** Without the flag a URL already in the vault is a `duplicate (already clipped)`. With it the page is fetched, extracted and checked as for any clip (thin, login-form, decline), and then:

- The text is the same as any capture already holding the URL (the same SHA-256 of the stored text as its `source-hash`): nothing is written, no row is queued, the line is `unchanged (same text as raw/clippings/<name>.md); nothing written` and the exit code is 0.
- Otherwise a new clipping is written beside the old one. Its file name is the oldest capture's own name followed by ` (recaptured YYYY-MM-DD)` (the same as a first clip's name, unless the first clip took a later candidate name or the page title has changed since); its `title` is the page title followed by the same suffix; `created` is today; `source` is the same URL; `recapture-of` is the vault-relative path of the newest existing capture, as a quoted string, so a chain of recaptures reads in order. The older clipping is never edited. A second recapture on the same day with different text finds its name taken by another capture of the URL and is a `clash`; a name held by an unrelated document moves on to the next candidate name.
- `--slug=<name>` with `--recapture` is used exactly, with no suffix, and a taken name is a `clash`.
- A URL that is not yet clipped is clipped as usual, after the line `recapture: not clipped yet, clipping it normally: <url>`.

The newest capture of a URL is the one with the latest `created`, then the later file name. Consumers that assumed one clipping per URL now follow it: the topic index takes the topic of the newest capture (an older capture's topic is used when the newest has none, and every capture still answers for its own path); a re-clip request by URL selects the newest capture only, so `apply-reclips` does not overwrite the older evidence; a quarantine recorded for an older capture does not suppress the triage rows of the newer one; `known-urls.mjs --summary` counts a URL once, under the topic and quality of its newest capture. The ingest backlog is unchanged: two captures with different text have different `source-hash` values and are two rows, which `health --backlog` lists, and `health --json` reports no new defect for them. The recapture route is on `clip.mjs` only, not on the document clippers, `clip-confluence` or `clip-gh`.

**A page a person saved: `clip.mjs <url> --from-file <path>`.** For a login, consent or age-gate page or a thin page, `clip.mjs` says to save the page from a signed-in browser and record it with `clip.mjs <url> --from-file <path>`. A person saves the page from a signed-in browser and supplies the file. `<url>` is the page's real address and nothing is fetched, not even the plain-text fetch for a URL that looks like a text file. The path may be the next argument or `--from-file=<path>`.

- Accepted files are `.md`, `.markdown` and `.txt` (the page text) and `.html` and `.htm` (a page), matched without regard to case. A text file is the page text with the byte-order mark removed and trailing whitespace trimmed, not put in a fence; its title is its first heading, else the last part of the URL. An HTML file goes through the same extractor as a fetched page, run on the local file with the URL as the page address, and the archive-banner strip applies to it as to a fetched page.
- Refusals. An empty path, an extension that is not one of those, a folder or a missing file exits 2 with a `--from-file:` message, before anything is written or queued. A file over 1 MiB, or with a NUL byte or 2% undecodable text, is not written and is queued as an `attention` row (`supplied file refused: ...`). An HTML file the extractor cannot read is queued as `attention` and nothing is written.
- Checks. A supplied page under 100 words is queued as a `thin` row (a `wrong-node` row when an HTML page's description is missing from its extracted body) and is never declined. The short-page rule of a fetched page applies to it: three headings and 20 words are written. A page judged to be a login, consent or age-gate page by the existing classifier (`lib/interstitial.mjs`) is queued as `wrong-node`, not written and not declined, and there is no override. The classifier compares the page's title with its text; for supplied text the title it uses is the last part of the URL. It cannot judge a title with no word of five letters or more, so a supplied gate page at a URL that ends in a bare id is not caught; that is a limit of the 0.81.0 classifier, now reachable by this route.
- The decline gate applies as for any clip: an active decline on the URL prints `declined previously` and writes nothing, and `--override-decline` (an automatic decline only) or `--supersede-decline="reason"` lifts it once the clipping is written. A refused file leaves the decline in place. A landed manual capture closes an open row for that URL.
- The clipping carries `extraction: manual`, `supplied-sha256` (the SHA-256 of the supplied bytes) and the usual `source-hash` (the SHA-256 of the stored text); the supplied file's name and path are not recorded.
- `--from-file` on a URL already clipped is a `duplicate`; with `--recapture` it writes a dated recapture, or `unchanged` when the text is the same.
- `triage` and `health` treat `manual` as a method and raise no row and no defect for it, as for `ocr` and `rendered`. The re-clip route (`apply-reclips`) refuses a clipping with `extraction: manual`, because a fetched page would replace the text a person supplied: it is listed in the report's `refused` and is not a target (a dry run selects 0 for it). The reason says the text was supplied by a person and that the way to refresh it is `clip.mjs <url> --from-file <path> --recapture`. The refusal is not a failure: no triage row is queued and the exit code is unchanged. A quarantine is not refused.

**The decline log as a command: `scripts/decline.mjs`.** `--supersede-decline` acts only after a clipping is written, so on a URL already clipped it did nothing. `decline.mjs list [--json]` prints every entry of `.wiki-master/declined.json`, expired and superseded ones too: URL, reason, date, expiry, and whether it is active, expired or superseded (tab-separated; `--json` is an array of objects). `decline.mjs show <url>` prints the one entry (and its earlier decisions) and exits 1 when there is none. `decline.mjs supersede <url> --reason "<text>"` marks the active decline for the URL superseded with the reason and the date, whether or not the URL is clipped, and prints `superseded`; with no active decline it exits 1 and writes nothing. A missing reason, an unknown subcommand or a wrong number of URLs exits 2. The only file it writes is the decline file. After a supersede the decline gate no longer blocks the URL.

**Discovery's dedup set as a command: `scripts/known-urls.mjs`.** It reads the clippings as the clipper does (the first `source:` line of each `.md` file directly under `raw/clippings`, compared after normalizing the URL), so a URL it calls `new` is one the clipper would not call a duplicate. With no option it prints the known URLs, normalized and sorted, one per line; `--count` prints the number. `--check <url>...` prints one line per URL in the order given, without the URL: `new`, `clipped raw/clippings/<name>.md` (the first capture, with ` (+N recapture)` when N later captures name another clipping of the same URL in `recapture-of`) or `declined: <reason>`; a clipped URL is reported as clipped even when it also has a decline. `--summary --topic "<topic>"` prints the number of pages the topic holds (a URL once, under the topic and quality of its newest capture), the count per quality tier, the open triage rows for the topic by kind, and the line `Declines are not recorded per topic.` Every mode only reads. A missing or conflicting option exits 2.

**Limits.** Recapture does not exist for `clip-pdf`, `clip-docx`, `clip-pptx`, `clip-xlsx`, `clip-confluence` or `clip-gh`. Stopping `clip.mjs` from declining on the thin heuristic is not part of this change. The clip lines for a thin or wrong-node page and for a login, consent or age-gate page, and the gate reason of the classifier, now point to `--from-file`. The browser-render challenge text (`scripts/lib/render.mjs`) and the corrupt-file messages of `clip-docx`, `clip-pptx` and `clip-xlsx` still say to clip manually: a saved page is the wrong route for a corrupt file, and the render message is left for a later change.
